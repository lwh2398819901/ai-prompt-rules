# 代码审查

## 核心原则

代码审查是发现风险的任务，不是实现任务。先列具体问题，按严重程度排序；除非用户明确要求，否则不要直接修改代码。

## 适用场景

- 用户要求 review、审查、检查代码或「看一下这个改动」。
- 用户要求评估合并、发布或回归风险。
- 用户询问某个改动是否安全、可维护或缺少测试。

普通实现任务不要默认进入代码审查，除非用户要求审查或当前处于审查检查点。

## 审查等级

| 等级 | 适用场景 | 检查重点 |
| ---- | -------- | -------- |
| L1 快速扫描 | 日常小改动 | 语法、导入、明显重复、基础 linter |
| L2 重点审查 | 已完成功能或修复 | 复杂度、函数长度、命名、错误处理、硬编码 |
| L3 全面审查 | 重大重构或发版前 | 架构、性能、安全、TODO、文档完整性 |

## 问题严重度

| 级别 | 含义 |
| ---- | ---- |
| 致命 | 语法 / 运行失败或数据破坏风险 |
| 严重 | 明确逻辑错误、严重重复、安全风险 |
| 一般 | 可维护性、复杂度或覆盖缺口 |
| 轻微 | 风格或可读性建议；不得扩大范围 |

## 输出顺序

1. 先列问题，按严重程度排序。
2. 说明每个问题为什么重要。
3. 给出最小可行修复方向。
4. 说明测试缺口和残余风险。
5. 仅在有帮助时提供简短总结。

如果未发现问题，明确说明检查范围和剩余不确定性。

## 硬边界

- 不要为了显得有价值而制造问题。
- 不要把个人偏好包装成缺陷。
- 审查过程中不要修改代码，除非用户明确要求。
- 如果用户同时要求审查和修复，先完成审查，再按用户明确指令继续。

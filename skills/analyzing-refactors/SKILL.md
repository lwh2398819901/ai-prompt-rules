# 重构分析

## 核心原则

重构分析默认只识别必要的结构改进，不直接改变行为。只建议真正降低复杂度、提升可预测性或对齐既有架构的改变。

## 适用场景

- 用户要求重构分析、cleanup plan、结构审查或整理结构。
- 用户询问哪些代码可以删除、重命名、重组或简化。
- 用户希望先获得高层重构报告，再决定是否实施。

窄范围 bug 修复不要默认启用本技能，除非用户明确要求重构分析。

## 必做检查

- 阅读相关应用代码和现有模式。
- 检查当前结构是否违反可维护性原则。
- 识别重复、过度抽象、过时代码、命名问题和架构不一致。
- 说明已搜索范围和剩余不确定性。

## 建议分级

按优先级组织建议：

| 优先级 | 适用情况 |
| ------ | -------- |
| 高 | 当前结构会制造 bug、阻塞变更或隐藏核心行为 |
| 中 | 复杂度可观察，且可能拖慢后续工作 |
| 低 | 机会型清理，收益有限 |

每条建议包含：

- 收益
- 风险
- 最小改动方向
- 验证方式

## 输出位置

如需生成报告文件，默认写入项目上一层的 `<项目名>-tmp` 临时目录，除非用户指定其它位置。

## 硬边界

- 分析阶段不要修改代码，除非用户明确要求。
- 不要为了改变而建议改变。
- 如果某些内容不需要改，明确说明不需要改。
- 除非用户明确要求改变行为，否则保持行为不变。
